# Rooms and spaces in an rvt-rs IFC export

This page is for the importer of an rvt-rs export: what an `IfcSpace` is and which property says so, what it holds for each release, the one property that says whether to trust its area, what is measured against Revit's own export and where, and what is not. Every `IfcSpace` rvt-rs writes in a geometry export (the default) carries that property: rooms, Revit Spaces, family instances written as spaces and Areas alike. An export with no geometry (`typed_no_geometry`) has no outlines and no `SpaceOutlineSource`, and every `IfcSpace` of it still carries `SpaceKind`. The evidence is in [RE-313](../reports/element-framing/RE-313-space-outlines-measured.md) and, for the rooms whose stored solid the first reader did not close, [RE-316](../reports/element-framing/RE-316-room-solids-resolved.md); the earlier findings are RE-29, RE-101, RE-102, RE-117, RE-153, RE-196, RE-255 and RE-296, and RE-191 and [RE-317](../reports/element-framing/RE-317-area-boundaries.md) for Areas.

## Which property answers which question

| Question | Read | Do not |
|---|---|---|
| What is this space: a room, an Area, a Revit Space (MEP) or a family instance written as a space? | `RvtElementRecordGeometry.SpaceKind` (`room`, `area`, `mep_space` or `family_instance`), on every `IfcSpace` | filter on the values of `SpaceOutlineSource`, or infer the kind from a name, a number, a predefined type or a body |
| Is the plan area of its body the space's, and where did its outline come from? | `RvtElementRecordGeometry.SpaceOutlineSource` (the table below) | use it to tell an Area from a room |

`SpaceKind` is taken from the Revit class of the record the space was read from, not from its outline, so it does not move when an outline is read by another rule. `SpaceOutlineSource` says only where an outline came from, and its values change with the rules that read outlines: a release that reads Areas by another rule gives them another value, as the plan topology of #1428 does (`area_plan_topology`, and `area_plan_topology_unchecked` for the Areas of Revit 2025 to 2027), so a filter written for the values of an earlier release would catch none of them. The same value is `space_kind` in the MCP server's `list_rooms` and a `space_kind` column, the last, in the room schedule (`rvt-schedule --schedule rooms`).

| `SpaceKind` | The space is | Its `SpaceOutlineSource` is |
|---|---|---|
| `room` | a Revit room (class `Room`) | `stored_solid`, `stored_solid_faces`, `stored_solid_approximate`, `stored_solid_edges`, `record_box` or `saved_mesh` |
| `area` | a Revit Area (class `Area`), with a body or without one | `area_boundary`, `area_boundary_joined`, `area_plan_topology` or `area_plan_topology_unchecked` (both #1428, the second on Revit 2025 to 2027 and on an Area drawn from lines whose partition copies disagree, #1434) or `none`; `area` holds exactly where `SpaceOutlineSource` is one of these |
| `mep_space` | a Revit Space (class `Space`, MEP). None is written today (below) | `record_box` or `family_body` |
| `family_instance` | any other element whose own "Export to IFC As" names `IfcSpace` (#763): a family instance or a mass in the files measured, the 42 "Turning Free Space" discs and two "VOLUME" families of the BIM4LCA office, and in principle a wall or a floor, for which it is the nearest of the four | `record_box` or `family_body` |

Every `IfcSpace` rvt-rs writes carries `SpaceKind`, bar the one case below, in a geometry export (the default) and in `typed_no_geometry`, whatever the release: the document exporter adds it after every other step, so `rvt-ifc`, Python's `write_ifc`, the MCP server's `export_ifc` and the browser viewer all write it. It goes in the space's `RvtElementRecordGeometry`, which is made for a space that has none. The one path that does not carry it is the library function `ifc::build_ifc_model`, which writes whatever property sets its caller hands it and which no rvt-rs exporter uses. `RvtElementRecordGeometry` is rvt-rs's own set, not an IFC4 one: `SpaceKind` is in none of `Pset_` counting, `decoded.parameter_value_count` and the property-set census (`psets_vs_ifc`), which read the `Pset_` sets only.

A space whose property set is not `RvtElementRecordGeometry` is written without `SpaceKind`, never with a guess, and the diagnostics count it: `exported.spaces_without_kind` (and `rvt-ifc` says so in its summary), with `exported.space_kinds` giving the others by kind. Only a wall or a floor read through the schema walker, whose properties are in `RvtWallGeometry` or `RvtFloorGeometry`, with an "Export to IFC As" that names `IfcSpace`, could be one, and no model measured has one. A wall or floor record that is read as a partition record and names `IfcSpace` does carry the kind, `family_instance`. The expectation is zero, and `tools/re/space_kinds_vs_ifc.py` makes it a check: it fails on any `IfcSpace` with no kind, with another value, with an outline source it does not know, or with a kind that disagrees with its outline source (an `area` outside the Area values above, or a space of another kind inside them). Measure sums its result over the run (`--total`) and judges each model on its counts, not its verdict word; it fails a model whose spaces are not the number its own export counted, so a check that saw none of a model's spaces cannot pass, and a geometry export whose spaces have lost their `SpaceOutlineSource`; an export with no geometry (`typed_no_geometry`) has none by design and passes with the agreement not checked.

`mep_space`: rvt-rs reads no Revit Space from a file's partition records (no MEP space category is among those it reads), so none is written as an `IfcSpace` today. Only the schema walker names the class `Space`, and no class census of Measure run 42027776156 (93 `diagnostics.json`) lists it, among them the 12 Autodesk `rme_*` samples', which list ducts, pipes and rooms. That says what rvt-rs reads and writes, not whether the files hold Revit Spaces: the census cannot tell.

Measured on Measure run 42027776156 (head 04d1b101, base main 5988d839; diagnostics, the check's own result and the MCP server's rooms, counts only for the models it keeps as counts): the 117 models and Autodesk samples it exported hold 4,453 `IfcSpace`s, 3,733 rooms, 628 Areas and 92 family instances, 66 of the 117 holding spaces, and none without a `SpaceKind` (`exported.spaces_without_kind` is 0 on each) or with another value. The 93 exports that keep their own results hold 3,421 of them: 2,857 rooms, 472 Areas and 92 family instances. The other 24 are kept as counts only: 18 held-out models (330 rooms, 6 Areas) and the six saves of `rac_advanced` scored against the three.js IFC2X3 export (546 rooms, 150 Areas). `tools/re/space_kinds_vs_ifc.py` passes on every one of the 117: no space has no kind or another value, none has an outline source it does not know, no `area` lacks an Area outline source (all 628 have one) and no room or family instance holds one. The BIM4LCA office, as built and at permit, holds 308 spaces: 234 rooms, 30 Areas and 44 family instances (its two terrain variants 9 each: 7 rooms and 2 family instances). Autodesk's `rac_advanced` holds 25 Areas and 91 rooms on every save but 2021's, which held 91 rooms and no Area until #1434 and now holds the 25 Areas too (drawn from the plan topology alone, and marked unchecked); Snowdon Towers' architectural sample holds 54 rooms and 101 Areas and its structural one 7 Areas; `rst_basic` holds its one Area on each save of 2024 to 2027. Core Interior's 116 spaces are rooms, RE1 Architecture's 11. Against main on that run, the 66 models and samples with spaces differ in their `ifc.sha256` (which leaves out the `FILE_NAME` and `IFCOWNERHISTORY` lines) by the added property alone, the other 51 have the same `ifc.sha256`, `diagnostics.json` differs only by `exported.space_kinds` and `exported.spaces_without_kind`, `mcp answers` and the held-out `counts.txt` differ only by the kind lines and the three checks `mcp answers` gained, and every other scorer's output is equal.

## Which `IfcSpace`s rvt-rs writes

| Source | `IfcSpace` | Body |
|---|---|---|
| A Revit room | `Name` is the room's number, `LongName` its name, `PredefinedType` `SPACE`, in the storey of the Level its record names | the outline of the room's stored solid, or the record's bounding box (below) |
| A Revit area (Revit 2024 to 2027; Revit 2015 to 2023 only where the body is proven, RE-324, RE-333) | the same naming | the region of Revit's own plan topology for the Area where that is read and passes its checks (RE-333), else the region its area boundary lines enclose around its point, up to the Level above it (below); none where neither is proven: the space then has no `Representation` |
| A Revit Space (MEP) | not written today: rvt-rs reads no MEP space category from the partition records (`mep_space`, above); an `IfcSpace` of the schema walker's class `Space` would have no predefined type | its record's box (`record_box`) unless a carrier draws more (`family_body`) |
| A family instance whose "Export to IFC As" names `IfcSpace` (#763) | named `Family:Type:ElementId` as Revit's export names other family instances | its record's box, turned with the instance (`record_box`), until a carrier draws its family. Where its family draws no model form, Revit's export leaves the instance out, and rvt-rs will too once PR #1279 (RE-312, for #1262, parking bays) lands |

A room carries its ElementId (`RvtElementRecordGeometry.ElementId`), its number and name (`RoomNumber`, `RoomName`), `Pset_SpaceCommon.Reference` (name and number) and `IsExternal` where measured, and `Pset_SpaceCoveringRequirements.FloorCovering` where the room's Floor Finish is read. A room's `Qto_SpaceBaseQuantities.Height` is written where its record holds the solid's faces (RE-255) and its `NetVolume` where every vertical face of the solid runs from floor to ceiling, on Revit 2024 and 2025 (RE-296). `Qto_SpaceBaseQuantities` never holds an area: take the area from the body.

## Which property says whether to trust the area

Read `RvtElementRecordGeometry.SpaceOutlineSource` on the `IfcSpace`. It says where the outline came from and so whether to trust the area. It does not say what the space is (`SpaceKind` does, above), and its values are not a set to filter on:

| Value | The body is | Its plan area is |
|---|---|---|
| `stored_solid` | the outline of the room's stored solid, extruded to the room's height, read by the exact walk of RE-101, with each round column the room surrounds taken off as a void and one against a wall as a notch (RE-334) | Revit's room area: within 0.1% of Revit's export on every `stored_solid` room scored below by the scorer's upward faces except one, the permit office's STAIRCASE room 2611271 at 66%, which by Revit's floor is within 0.1% like the others (221 of 221 as built, 222 of 222 at permit; RE-313 §2, §3, RE-316 §3) |
| `stored_solid_faces` | the outline of the room's stored solid, read from the faces its solid lists, up to the solid's own end, where the walk did not close them: their edges close as the walk reads them (RE-316) | Revit's room area: within 0.1% on 9 of 9 office rooms as built, by every metric. Bounded by the solid's list of objects and a gap, not by the walk, so a closed loop of another element's faces inside the room's box would be read as the room's: that is why it is labelled apart (RE-316 §2, §3) |
| `stored_solid_approximate` | the same, as the boundary of a region, a column that overlaps a wall taken off it or an end of one wall edge lying on another, or up to 0.02 ft short of the room's record box on a side | approximate. Of the office's 15 room scores (4 as built, 11 at permit) 10 are within 0.1% of Revit's floor area and 5 are 0.45% to 0.68% under it (four rooms, 1671995 in both files): Revit's export does not take such a column off the room, and nothing in the file says which. The room schedule leaves the area blank (RE-316 §2, §3) |
| `stored_solid_edges` | the outline of the floor of the room's stored solid, read from the solid's edges, where neither the walk nor the span reads one (Revit 2024; #90, RE-374): each edge of the floor is drawn as the wall it meets, between its ends on that wall, so a wall face that is not a rectangle gives its real end, which the face's box does not. Read only where every face of the solid is vertical or horizontal, every edge's two planes give it the same ends, and the solid holds no point between its floor and 4 ft above it but on a vertical edge, so that up to that height the room is a prism of its floor | It reads two rooms of the models measured: the BIM4LCA office's 3095831 at building permit, 1864.737 ft² against the 1864.74 of Revit's IFC4 export, and Snowdon Towers' 830902, 304.059 ft² against Revit's 304.058 (`Vim.Room.Area` of the model's 2027 edition, a later save, local only). On every other room of Autodesk's samples, the office and the Revit 2025 models that the walk or the span reads and it accepts, it gives the same outline, to 0.01 ft² and 0.001 ft on the box. Refused, and kept as `record_box`, where a raised floor, a step, a pocket or a bulkhead lies lower: Snowdon Towers' room 2181757, whose floor is 5172.857 ft² and whose section at 4 ft above it is Revit's 5177.493, keeps its box (RE-374) |
| `record_box` | the record's bounding box (turned with a family instance that is turned) | the box's area, not the space's. It equals the space's only when the space is a rectangle; the area is Revit's on none of the office's room scores that keep their box (1 room at permit, 3095831; RE-316 §4) |
| `saved_mesh` | the mesh Revit saved for the room (`rvt-ifc --saved-meshes`) | the mesh's; not scored |
| `area_plan_topology` | the loop of Revit's own plan topology for the Area: its area boundary lines moved by their area rule's offsets (to a wall's face, say), arcs written as arcs (three-point `IfcIndexedPolyCurve` arcs, a span over a half turn as two), met where the moved lines cross, its holes the components it encloses, extruded from its Level to the Level above (RE-333). Used first, wherever it is read and passes its checks: the rebuilt loop has the area Revit saves for its circuit (`PlanCircuit m_area`, to 1e-6) and holds the Area's point in no hole. A point where a third line meets a straight outline is a vertex, as in `area_boundary` | Not measured against any Revit export on Revit 2025 to 2027 and on the Snowdon Towers 2024 samples (below). `area_plan_topology` is the topology's own outline source value, distinct from the lines' values (`area_boundary`, `area_boundary_joined`), for Revit 2015 to 2024. It is not split inside 2024: a 2024 Snowdon Towers Area and an office Area share a release and a code path, and say the same. Revit 2025 to 2027, and the Areas of `rac_advanced`'s 2021 save, say `area_plan_topology_unchecked` (next row). On `rac_advanced`'s 2020 save all 25 Areas are within 1e-6 relative in area and within 0.01 ft in outline of the three.js IFC2X3 export, which nothing of the topology was read off; the office's 30 have the regions and the vertex sets their `area_boundary` had, ring for ring: as built the outline starts at another vertex of the same ring in 3 of them and the holes of 6 come in another order (at permit, 2 and 6) (RE-333 section 8). The export is IFC2X3, counted apart, never used to remove a value. The counts of what is written (which exports move, the refusals, the held-out and racadv pairs, the gate) are from Measure run 42017400629 on `5008247d`, the code before the `area_plan_topology_unchecked` marker, and the bodies by source from run 42003913780 on `bcb02107`, whose set of moved exports it equals; the vertex-level and per-save equality figures are from the archived head `e9124b3a` of #1371 (runs 41894715743 and 41894722135) and were not re-read. |
| `area_plan_topology_unchecked` | the same region, drawn the same way, of an Area of Revit 2025, 2026 or 2027 (`partition_area_records::area_release_unchecked`; Griffin, 2026-11-05, "Mark 2025 to 2027 in the file"), or of an Area drawn from lines whose partition copies disagree (`partition_area_records::area_unchecked`, the one place both are decided; #1434: the 2021 save of `rac_advanced`, whose outlines are the later state of the model, which the only Revit export of the project does not show on 7 of the 25 Areas, the other 18 being equal to the earlier state it shows). Griffin decided that this save's Areas say the unchecked value (AskUserQuestion, 2026-11-05), although the 2022 to 2024 saves, the same later state, say `area_plan_topology` by his release rule | **Not measured against any Revit export**: none exists for these files. The loop drawn for each Area equals the area the file saves for it and holds the Area's point, and the same project's 2024 save gives the same Areas: Autodesk's `rac_advanced` has 25 on each of its 2025, 2026 and 2027 saves, which every Measure run that holds the four saves checks (the 2024 save says `area_plan_topology`, the later saves this value); the 2021 save's 25 equal the 2022 save's in every field the gate compares but this value, which every Measure run that holds both saves checks. The marker is in the file, so a reader sees the Areas that nothing outside the file checks |
| `area_boundary` | the region that the lines of the Area's scheme on its Level enclose around its point, its holes the loops directly inside, extruded from its Level up to the Level above it, both building stories | Revit's area space: within 0.1% of Revit's export, within 0.01 ft in outline, and with its lowest and highest vertex within 0.01 ft, on 60 of the 60 Area scores below, the office counted at both stages (RE-317 §5), measured when the office's Areas were drawn from their lines; the office's Areas now say `area_plan_topology` with the regions and vertex sets they had, so this row is exercised only where the topology is not read, which no model of the gate is known to be |
| `area_boundary_joined` | the same region, where its outline runs along a stretch of a boundary line carried on to the line it joins, or along a connector between two parallel lines that stop at the same place (RE-330); written only where the plan topology is not read, and on `rac_advanced` it is read, so none of its Areas says it since RE-333 (they say `area_plan_topology`) | as `area_boundary`, within 0.1% in area and 0.01 ft in outline of Revit's: the only external check of an Area drawn from lines carried on to their joins is an IFC2X3 export of Autodesk's `rac_advanced` from the three.js repository, by a build of Revit 2021's exporter whose string ends "IU alternativa 21.0.0.383" (publisher not established), showing the project's 2015 to 2020 state, against which the joins were read off and then scored (in-sample); the 2022 and 2023 saves are also checked against the 2024 save's reader, and no Revit IFC4 export of these Areas exists (RE-330). Never used to remove a value or to settle a disagreement between exporters |
| `none` | no body (an Area whose boundary is not proven) | not available |
| `family_body` | a Revit Space or a family instance written as an `IfcSpace`, drawn as more than its box; its `BodySource` says how | not scored |

A room's `BodySource` is `partition_element_record_bbox` whichever of the stored-solid or `record_box` values it has, because the placement and the height always come from the record's box: read `SpaceOutlineSource`, not `BodySource`. An export from before this property (rvt-rs 0.12.x and earlier) says the same through `ProfileSource` (`partition_room_solid_faces`, since RE-316 `partition_room_solid_faces_resolved` and `partition_room_solid_faces_approximate`, and since RE-374 `partition_room_solid_edges`) and `ProfileResolved`. A room with `stored_solid_faces`, `stored_solid_approximate` or `stored_solid_edges` carries no `NetVolume`.

The export also counts the spaces drawn as their record's box (rooms and family instances alike), so an importer can check a whole file before reading a space:

- `exported.bounding_box_spaces` in the diagnostics JSON (`rvt-ifc --diagnostics`), out of `exported.by_ifc_type.IFCSPACE`;
- `exported.resolved_outline_spaces` (`stored_solid_faces`), `exported.approximate_outline_spaces` (`stored_solid_approximate`) and `exported.edge_outline_spaces` (`stored_solid_edges`), the rooms whose outline was not read by the exact walk;
- a line in `rvt-ifc`'s summary for each: "N of M spaces are their record's box", "N rooms take an outline resolved from the faces up to their stored solid's end", "N rooms take the outline of their stored solid's floor, read from its edges", "N rooms take an approximate outline";
- `exported.space_kinds` (the spaces by `SpaceKind`) and `exported.spaces_without_kind` (those with none, expected zero, and said in the summary when not).

Areas as spaces, with a body where their boundary lines prove one, are read on Revit 2024 to 2027 and, by the same rule, on Revit 2015 to 2023. An Area's region is the loop Revit's own plan topology keeps for it where that is read and passes its checks (RE-333; it says `area_plan_topology`): its area boundary lines moved by their area rule's offsets, arcs included, checked against the area Revit saves for the loop and against the Area's point. Otherwise it is the region the lines' arrangement gives: a line that stops short of the line it joins is carried on to it, and two parallel lines that stop at the same place a wall's thickness apart are joined by a connector, where their records name each other (RE-330). A group of lines that cannot be read as a whole (a line in a non-primary design option, at a stray height, with a copy that names another Level or scheme or lies at another height, or missing) gives no region of either kind. A group whose lines have copies in several partitions that differ only in box or in the lines they name, each naming the group's Level and scheme at its height (a file saved with both states of the model), gives the plan topology's region alone, which reads the current copy of each line and passes the same checks (#1434). Where the plan topology and the lines' arrangement both give a region and they are not the same one (the same net area, the same outline within 1e-4 ft), the Area has no body and says `area_regions_disagree` in `exported.area_body_refusals`; none of the public models refuses one (Measure run 42017400629 on `5008247d`). Where the topology was read and failed a check (`area_circuit_area_differs`, `area_point_outside_circuit`, `area_arc_not_finite`, `area_circuit_too_large`), the lines' region is not drawn in its place. On Revit 2025 to 2027 the Areas are checked against the same project's 2024 save (Autodesk's `rac_advanced`: the same 25 Areas, numbers, names, storeys and bodies on each). A Snowdon Towers 2025 file awaits a recorded source. On the recorded Autodesk 2024 Snowdon Towers samples rvt-rs writes 101 Area spaces (96 with a body) on Architectural and 7 (2 with a body) on Structural, where main writes none (RE-333 section 8). Not measured against any Revit export (Griffin, 2026-11-05, "Ship, labelled", then "Same-project gate"): the Areas of Revit 2025 to 2027 and the 108 Area spaces of the recorded Autodesk 2024 Snowdon Towers samples (101 Architectural and 7 Structural written, 96 and 2 with a body; the bodies are from Measure run 42003913780 on `bcb02107`, Architectural's refusals from run 42017400629 on `5008247d`, Structural's total from `e9124b3a`). They are written by default. The Areas of Revit 2025 to 2027 say `SpaceOutlineSource` `area_plan_topology_unchecked`, so that the file shows that nothing outside it checks them (Griffin, 2026-11-05, "Mark 2025 to 2027 in the file"); the Snowdon Towers 2024 samples' Areas say `area_plan_topology`, because a 2024 file shares its release and code path with the office's, whose Areas Revit's IFC4 export checks, and that release is not split. The evidence is that the loop drawn for each equals the area Revit saves in the file for that loop (`PlanCircuit m_area`, to 1e-6) and holds the Area's point and, on 2025 to 2027, the same project's 2024 save gives the same Areas. They stay written only while the Areas of rac_advanced on its 2025, 2026 and 2027 saves equal its 2024 save's, Area by Area, in GlobalId, number, name, storey, outline source, body area, top surface, height and lowest vertex (Griffin, 2026-11-05, "Same-project gate"). Every Measure run of the samples that holds the four saves checks it with `tools/re/areas_across_saves.py` and fails on a difference, a missing or extra Area, other than 25 Areas or 25 bodies on a save, an Area with no storey, or a missing save; a run with fewer than the four saves (a narrower `sample_years`) checks nothing and prints a notice. Measure is not a required check: a failure blocks landing by the landing rule, read before merging. It compares rvt-rs with itself and cannot catch an error the 2024 read shares with the later reads. The seven held-out Revit 2025 to 2027 models write no Area and their exports are byte-identical to main's, so they test nothing here. The counts of what is written (which exports move, the refusals, the held-out and racadv pairs, the gate) are from Measure run 42017400629 on `5008247d`, the code before the `area_plan_topology_unchecked` marker, and the bodies by source from run 42003913780 on `bcb02107`, whose set of moved exports it equals; the vertex-level and per-save equality figures are from the archived head `e9124b3a` of #1371 (runs 41894715743 and 41894722135) and were not re-read. On Revit 2015 to 2023 an Area is written only where its region and body are proven; the others are not written and are counted by reason in `skipped` (`area_without_proven_body`, RE-324). On Autodesk's `rac_advanced` all 25 Areas are drawn on every save; the 2021 one, which holds two copies of 16 lines, was refused (RE-324) and is drawn from the plan topology alone since #1434. What those Areas rest on: the only external check of an Area drawn from lines carried on to their joins is an IFC2X3 export of Autodesk's `rac_advanced` from the three.js repository, by a build of Revit 2021's exporter whose string ends "IU alternativa 21.0.0.383" (publisher not established), showing the project's 2015 to 2020 state, against which the joins were read off and then scored (in-sample); the 2022 and 2023 saves are also checked against the 2024 save's reader, and no Revit IFC4 export of these Areas exists (RE-330). The plan topology's Areas were not read off that export: the 25 Areas of the 2020 save are all within 0.1% in area and 0.01 ft in outline of it, with none extra and none missing, and the 16 that the joins draw equal their topology loops on every save (RE-333 section 8). The first rule for 2015 to 2023, writing every placed Area as 2024 does, wrote spaces Revit's export lacks on a held-out project (below).

## What is measured, and where

`tools/re/space_profiles_vs_ifc.py` meshes both exports, moves them into Revit's internal feet and compares the plan union of each space's upward faces. It prints four figures, each on its own line:

- **area**: the plan area, within 0.1% of Revit's;
- **boundary**: the largest distance from a point of either outline to the other's outline, within 0.01 ft. This is the room's outline, and the figure used for "outline" in the table and in the text below;
- **outline**: the largest distance from a vertex of either mesh's upward faces to the other's outline, within 0.01 ft. Revit meshes a ceiling step inside a room as an upward face of its own, and its vertices count against this one, so it reads some correct outlines as wrong (RE-313 §3). The CI gate pins both. These three read the faces of Revit's mesh that point up, within 25 degrees of vertical, so a room under a stepped or sloped ceiling is read as the flat part of it: `tools/re/space_overlaps_vs_ifc.py` also measures the plan area of each space's floor (its downward faces) and of every face projected, in both exports, and counts the rooms within 0.1% of Revit's by each (RE-316 §3). The floor is the room's plan.
- **height**: the lowest and the highest vertex of either mesh, within 0.01 ft: the base and the top of the space, so its height. It is printed on its own line and for each kind of space (RE-317); it is 306 of 306 spaces in both exports on the office as built and 308 of 308 at building permit.

A room's phase is `RoomElem.m_phaseId` (not its created phase, which is unset; RE-326), and Revit's exporter leaves out a room whose phase is not the export phase, the project's last unless the export setup or a view names another. rvt-rs does the same: such a room is not written, the diagnostics count it in `skipped` as `room_not_in_export_phase` with the phase it sits in, and `rvt-ifc --phase <name|id>` chooses another export phase, exactly (naming the last phase writes no room that an earlier phase holds). One fallback, a choice by Griffin (2026-11-05, #1359): where no phase is named and the project's last phase holds no room, the rooms written are those of the latest phase that holds any, since rooms all in one phase cannot overlap. The diagnostics name that phase and count its rooms in `room_phase_fallback`, `rvt-ifc` prints a line, and Python raises a `RuntimeWarning`; every other element still follows the last phase. A room whose phase is unset, unread or not one of the project's is written, does not count towards the last phase holding a room, and so is an Area or an MEP space. Measured when the phase rule was added: all 621 rooms of the 12 models with a Revit export are in the last phase and in Revit's export, so none of them is changed by the rule or by the fallback (unfiltered Measure, run 41784044966: of 111 exports 12 move, the `rac_basic_sample_project` saves of Revit 2016 to 2027, and 99 are byte for byte as before, the held-out models included). Unmeasured: a Revit export made at the last phase of a project whose last phase holds no room, because none exists, so the fallback is a choice and not a measurement of Revit's default; and a Revit export made with the default setup that leaves a room out for its phase, because no project in the corpus has one. The only room outside its last phase is in Autodesk's `rac_basic_sample_project` (14 rooms in Working Drawings, the second of three phases, and none in Learning Content, the last); a public Revit 2018 export of it holds all 14, which rvt-rs writes with `--phase "Working Drawings"` (14 of that export's 17 `IfcSpace` by GlobalId, no other entity changing) and, since the fallback, by default (Measure runs 41784415396 and 41784419457 measured `--phase`; the default of the fallback, Measure run 42035308270 at `ea0c7449`, writes 14 `IfcSpace` of kind `room` on each of the 2016 to 2027 saves, byte for byte the `--phase "Working Drawings"` export (run 42035315319) and 14 of the Revit 2018 export's 17 by GlobalId (run 42035335073), and moves no other model of the 111 compared, held-out ones included; RE-326 §9.4). ## Check it yourself

```bash
rvt-ifc model.rvt -o model.ifc --diagnostics model.diagnostics.json
python3 tools/re/space_profiles_vs_ifc.py model.ifc revit-export.ifc --list 10
python3 tools/re/space_kinds_vs_ifc.py model.ifc
```

The second command needs Revit's own IFC export of the same model, IfcOpenShell, NumPy and Shapely (`tools/ci/requirements-ifc.txt`). It prints the counts above, one line each (`area`, `boundary`, `outline`, and the same split by what the space is and its `SpaceOutlineSource`), and for every space off in area or outline, the area on both sides, the distances and `SpaceOutlineSource`.

The last needs only IfcOpenShell and no Revit export: it counts the `IfcSpace`s of the file by `SpaceKind` and exits 1 if any has none, has another value or disagrees with its `SpaceOutlineSource` (an export with no geometry has no outline sources, so the agreement is not checked there and those spaces are counted on a line of their own).
